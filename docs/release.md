# 段階ごとのリリース手順

4 段階それぞれの完成時点を、**注釈つきタグ**と **GitHub リリース**で固定する。タグは動かさ
ない。あとから直したくなったら `v1.1` を足す（`v1` を打ち直さない — 一度提出した点が消える）。

| 段階 | タグ | タイトル                    |
| ---- | ---- | --------------------------- |
| 1    | `v1` | 段階1: 字句解析             |
| 2    | `v2` | 段階2: 構文解析             |
| 3    | `v3` | 段階3: 意味解析             |
| 4    | `v4` | 段階4: コード生成           |

## 手順

すべて自分で実行する。タグを押す・リリースを作るのは外向きの操作なので、Claude は提案までで
止まる。

### 1. 状態を確かめる

```sh
mise run release:check
```

作業ツリーが綺麗で `mise run verify` が緑なら通る。落ちたら先にそれを直す。

### 2. その段階の仕様を確定させる

`docs/stages/stageN-*.md` の「達成した範囲」と「既知の未対応」を埋めてコミットする。半年後に
「v2 で何ができたか」を知りたくなるのはこの 2 節だけ。

### 3. タグを打つ

```sh
git tag -a v1 -m "段階1: 字句解析"
git push origin v1
```

`-a`（注釈つき）にすること。軽量タグは日付も作者も残らない。

### 4. リリースを作る

```sh
gh release create v1 \
  --title "段階1: 字句解析" \
  --notes-file docs/stages/stage1-lexer.md
```

`--notes-file` にその段階の仕様を渡せば、リリースページがそのまま成果物の説明になる。ソース
の tarball / zip は GitHub が自動で付ける。提出はそのリンクか tarball を出す。

ビルド済みバイナリを添えたいときは、リリースを作ったあとに:

```sh
mise run verify:build
gh release upload v1 build-verify/mpplc
```

macOS arm64 向けのバイナリなので、提出先の環境が違うなら添えない方がよい。

### 5. 次の段階へ

```sh
git switch -c stage2   # 任意。main で進めてもよい
```

段階をブランチで分ける必要はない。タグが各段階の点を保持しているので、`main` を育て続けて
問題ない。

## 確認

```sh
git tag -n                 # 打ったタグと注釈
gh release list            # リリース一覧
git diff v1..v2 --stat     # 段階間で何が増えたか
```

`git diff v1..v2 --stat` は、そのまま「段階2 で何を足したか」の説明になる。レポートを書くとき
に使う。
