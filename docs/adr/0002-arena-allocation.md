# 0002. 記憶域はアリーナで一括管理する

- 日付: 2026-09-27
- 状態: Accepted

## 背景

コンパイラは AST の節点、記号表の項目、トークンの文字列という小さな領域を大量に確保する。
MPPL の構文木は式ごとに節点を作るので、数百〜数千の割当てになる。一方でコンパイラは 1 回走って
終わるプロセスであり、途中で領域を返しても再利用する相手がいない。

エラー経路が問題になる。記録して続行すると決めた（[0003](0003-continue-after-errors.md)）ため、
解析の途中で作った部分木を捨てる場面が何度も出る。個別解放だと、そのたびに節点種ごとの解放
関数を正しく呼ぶ必要があり、二重解放と解放漏れの両方が起きやすい。

## 選択肢

| 案 | 利点 | 欠点 |
| -- | ---- | ---- |
| アリーナ（一括確保・一括解放） | 解放漏れと二重解放が原理的に起きない。エラー経路で何も考えなくてよい。割当てが速い | C の所有権設計の練習にならない。使用量の上限が読みにくい |
| 個別 `malloc` / `free` | 所有権設計の練習になる。ASan が漏れを検出してくれる | 節点種ごとに解放関数が必要。エラー途中の巻き戻しが煩雑。漏れがあっても 1 回走って終わるので実害が出ず、練習として成立しにくい |
| アリーナ + 大きな資源だけ個別解放 | 両方の練習になる | 境界をどこに引いたかを常に意識することになり、「どちらだったか」を間違える新しい事故が増える |

## 決定

アリーナで一括管理する。AST・記号表・文字列・ソースの全文バッファを含め、すべてアリーナから
取る。明示的に解放する資源は `FILE*` だけ。

付随して、トークンが持つ綴りは複製せず `source` のバッファを指す（ポインタ + 長さ）。例外は
`''` を含む文字列リテラルで、中身が綴りと違うためアリーナ上に複製を作る。

確保に失敗したら `mpplc: error: out of memory` を出して終了コード 1 で死ぬ。呼び出し側は NULL
検査をしない。

## 理由

エラーからの回復を伴うコンパイラでは、部分的に作った構造を捨てる場面が繰り返し現れる。そこで
所有権を追うコストが、得られる練習の価値を上回る。段階3・段階4 の本題は記号表と命令選択であり、
解放漏れの追跡ではない。

確保失敗で死ぬと決めたのは、回復できない失敗を 1 箇所に集めるため。呼び出し側に NULL 検査を
撒くと、そのほとんどが到達しない分岐になり、テストも書けない。

## 結果

- 呼び出し側から解放の記述が消え、エラー経路が短くなる。
- ASan は解放漏れを報告しなくなる（アリーナが最後に返すため）。代わりに**使用量が読みにくく
  なる**ので、極端に大きな入力で困ったら、そのときにアリーナのブロック数を測る手段を足す。
- トークンの綴りが NUL 終端されないため、扱うときは常に `len` と対で渡す規約が必要になる。
  `printf` は `%.*s` を使う。これを忘れると隣のトークンまで読む不具合になる。
- 覆す引き金: 生成物が常駐プロセスになる、または同一プロセスで複数のプログラムを続けて
  コンパイルする必要が出たとき。どちらも現在の外部仕様では起きない（1 ファイル 1 起動）。
