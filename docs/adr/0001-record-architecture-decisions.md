# 0001. 設計決定を ADR で残す

- 日付: 2026-09-27
- 状態: Accepted

## 背景

コンパイラを 4 段階に分けて実装する課題で、各段階の判断（解析方式、AST の所有権、エラー報告の
方針、目標機械）が後続の段階を縛る。段階が進むと初期の判断理由が思い出せなくなり、レポートで
「なぜこの方式か」を問われたときに再構成できない。

## 選択肢

| 案 | 利点 | 欠点 |
| -- | ---- | ---- |
| ADR を 1 決定 1 ファイルで残す | 決定した時点の判断が残る。差分が読める | 書く手間がかかる |
| コード中のコメントに理由を書く | 近くにあって読みやすい | コードが動くと消える。落とした案は書けない |
| 何も残さない | 手間ゼロ | 理由が消える |

## 決定

`docs/adr/` に 1 決定 1 ファイルで残す。覆すときは書き換えず、新しい ADR を足して古い方を
`Superseded` にする。

## 理由

コンパイラは前の段階の判断が後の段階の形を決める構造をしていて、「なぜ」がコードから復元でき
ない。コメントは扱っている対象が動くと一緒に消えるので、落とした案を残す場所にならない。

## 結果

「なぜ」を書く場所が決まったので、コード中のコメントは「何をしているか」に専念できる。決定の
たびに 1 ファイル書く手間は増えるが、対象は上に挙げた数件程度で、段階ごとに 1〜2 本に収まる。
覆した記録も残るため、レポートで判断の変遷を説明できる。
