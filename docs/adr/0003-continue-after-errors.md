# 0003. 字句・構文・意味のエラーは記録して続行する

- 日付: 2026-09-27
- 状態: Accepted

## 背景

外部仕様に `-fmax-errors=<n>`（エラーを n 個出した時点で打ち切る）を入れた。これは「1 回の実行
で複数のエラーを報告する」ことを前提にしたオプションで、最初の 1 件で止める実装なら意味を持た
ない。仕様とふるまいのどちらかを選ぶ必要がある。

## 選択肢

| 案 | 利点 | 欠点 |
| -- | ---- | ---- |
| 記録して続行する | 1 回の実行で複数の誤りが分かる。`-fmax-errors` が意味を持つ。gcc と同じふるまい | 構文解析では回復方法を決める必要がある。意味解析では偽陽性が出る |
| 最初の 1 件で打ち切る | 実装が単純。テストの期待値が短い | `-fmax-errors` が無意味になり、外部仕様と矛盾する。使う側は 1 件直すたびに再実行することになる |

## 決定

記録して続行する。`diag` がエラーを集計し、各フェーズは終わってから `diag_error_count()` を見て
次に進むかを決める。`-fmax-errors` に達したら打ち切る。

字句解析では `TOK_ERROR` という種類を作らない。問題の文字を飛ばして次の正当なトークンを返す。

## 理由

外部仕様に既に `-fmax-errors` を書いた。仕様を削るより、ふるまいを合わせる方が使う側に有益で、
gcc を参考にするという方針とも揃う。

字句解析については、続行のコストがほぼゼロである（読めない文字を 1 つ飛ばすだけ）。エラー
トークンを作らない方を選んだのは、作ると段階2 のパーサがそれを扱う分岐を持つことになり、
「パーサの入力は正当なトークン列」という単純な契約が崩れるため。

## 結果

- 段階2 で**構文エラーからの回復方法を決める義務**が生まれる。定番は「`;` か `end` まで
  読み飛ばして再開」。これを決めないまま続行すると、同じ位置で無限にエラーを出す。
- 段階3 で**偽陽性の抑制が必要**になる。未宣言の変数を使った式の型を検査すると、本当の誤りは
  1 つなのにエラーが 2 件出る。未解決の名前を持つ式は型検査を飛ばす、という形が要る。
- エラーがある入力に対しても後続フェーズが走りうるため、「エラーが 1 件でもあれば次のフェーズに
  進まない」という約束（[architecture.md](../spec/internal/architecture.md#段階間の約束) の 1）を
  main が守る責任を負う。
- 覆す引き金: 回復の実装が段階2 の本題を圧迫するほど重くなったとき。そのときは
  `-fmax-errors` を仕様から外し、この ADR を Superseded にする。
